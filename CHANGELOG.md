# Changelog

All notable changes to this project.

Unreleased
----------

The parity release: the reference `exclude_paths`, client and response-pass semantics, and the whole `SecurityConfig` through the facade's `Wiring`.

### Added

- Route country rules and the unknown client identity follow the reference `check_route_ip_access`: the route `ip_whitelist` / `ip_blacklist` verdict is combined with the route `blocked_countries` / `whitelist_countries` verdict (a route whitelist match no longer overrides a blocked country, `blocked_countries` is asked first, no loopback exemption on the route arm), the unknown client identity is denied by a route `ip_whitelist` or `whitelist_countries`, and a global `whitelist` denies it (it passed before). Verified against 2125 rows generated by running the reference (`tests/route_country.rs`)
- Client resolution with the reference rules: the connecting peer plus `X-Forwarded-For` through `trusted_proxies` and `trusted_proxy_depth`, IPv4-mapped peers canonicalized. A request with no peer and no resolvable client answers `403 Client address could not be determined` under `fail_secure` (check name `client_address_unresolved` on the `on_block` hook), after the exclusion decision. `GuardTransform::with_client_policy` and `ClientPolicy` install the policy (bare layers keep `fail_secure = false`), and `WebSocketGuardConfig::with_client_policy` gives the upgrade guard the same resolution
- `GuardExclusionScoped`, the request extension an `exclude_paths` request carries (the reference `guard_exclusion_scoped`), and the scoped pipeline it runs: route resolution, bans, the global IP, country and cloud rules, and the rate limit. The response pass runs scoped (metrics, security headers, CORS and the modifier, no return rules)
- `GuardTransform::from_security_config_with(config, &WiringOptions)` and `from_wiring(Wiring)`, with the telemetry agent injected through the facade's `TelemetryHandler`. `agent_stats()` now reports the wired sink and its degraded state, `telemetry()` exposes the fan-out, `spawn_dynamic_rules()` starts the dynamic-rule poll loop on request, and the cloud-range refresh runs per request at the cloud check position. New builders: `with_telemetry`, `with_dynamic_rules`, `with_cloud_refresh`, `with_auth_verifier`, `with_body_read_timeout`, `with_path_exclusions`. `GuardConfigError` gained the `Cloud`, `Redis` and `Geo` variants
- The `security_bypass` event for an all-checks-bypass route (`all_checks_bypassed`), whose request forwards with only the response modifier applied (no metrics, headers or return rules) and continues through the pipeline under `passive_mode`
- Body `return_pattern` rules now read the response body: the forwarded body is buffered when a rule needs it, bounded in time by `body_read_timeout`, re-emitted intact, and a read error or timeout answers the fail-secure `500`

- `route_resolution_strict`: a request no registered actix resource matches (`HttpRequest::match_pattern` is `None`, read from the app's resource map before routing) answers `500 Route resolution failed` and emits `route_unresolved` (log-only under `passive_mode`), firing `on_block`. New builder `with_route_resolution_strict`
- `body_read_timeout` now bounds the request-body read: a body that does not arrive in time answers `408 Request body read timed out` and is never forwarded
- Live config: the stages a dynamic rule can change (country, cloud, user agent, emergency mode, the detection toggle, the rate-limit and ban knobs) are read from the facade's live config on every request when the transform is built from a `SecurityConfig`
- Cargo features `redis` (forwards `guard-core-rs/redis`) and `agent` (builds the telemetry agent from the `agent_*` fields through guard-agent-rs, degrading unless `agent_strict`). `GuardConfigError` gained `Config` and `Agent`, and `LiveCell`, `LiveContext` and `LiveStages` are re-exported

### Changed

- The route's usage rules now run after the whole pipeline passed (just before forwarding), skipped for an unattributed request, so a request the pipeline blocks no longer counts toward a usage or frequency rule
- `from_security_config` validates the `SecurityConfig` first and returns `GuardConfigError::Config`; build an intentionally unvalidated wiring with `Wiring::build_unvalidated`
- `exclude_paths` uses the engine's reference matcher instead of an exact raw-path comparison: `/static` covers `/static/app.js`, percent-encoding and dot segments are resolved, and `exclude_paths()` reports the normalized entries. An excluded request is no longer exempt from the pipeline: bans, the global IP lists, country and cloud rules and the rate limit apply, and the request is counted in the metrics. Tests that encoded the old exact-match bypass were updated
- `from_security_config` builds through `Wiring`, so the fields it used to drop now land: geo country rules and `geo_ip_handler`, `block_cloud_providers`, `endpoint_rate_limits`, `enable_rate_limit_auto_ban`, `custom_request_check`, `auth_verifier`, `custom_response_modifier`, `on_error`, `cors_expose_headers`, `trusted_proxies`, the telemetry and event bus, dynamic rules, and the redis stores when `guard-core-rs` has its `redis` feature. The response processor now shares the ban manager with the ban stage, so a return-rule `ban` is enforced by the next request. A config with `fail_secure = true` (the default) rejects a request that carries no peer address
- The custom response modifier runs even when no response processor is installed, and exactly once when the processor already carries it
- The HTTPS stage matches `trusted_proxies` against the connecting peer instead of the `Host` header, and the request scheme is the transport's own instead of the `Forwarded` / `X-Forwarded-Proto` claim, so a forged forwarded protocol no longer skips the redirect
- Whitelisted and exempt IPs are now skipped by the geo, cloud and user-agent stages: the gate's skip state was read before the gate ran
- A route carrier's `auth_required` and `api_key_required` fall back to the config's global `auth_verifier`
- Documentation: the README no longer contradicts itself on the status route and the WebSocket guard, the stale status and Makefile statements are corrected, and the new config surface, client policy, scoped exclusions and agent injection are documented

### Note

### Added

- The `get_cloud_providers_to_check` route-over-global resolution (the RC2 actix leg, over guard-core-rs#105's `decide_route`): the carrier route's `block_cloud_providers` list replaces the global one for the request (an empty route list falls back to the global config), an invalid route selector fails secure (the reference validates at decoration time), the global lane stays untouched off-route, and the `clouds` bypass skips the whole arm; five end-to-end twins drive the override, the off-route hold, the fallback, the fail-secure arm, and the bypass
- The carrier's stage knobs at the per-stage seams (the RC1 actix leg): the `(method, path)` carrier's remaining reference knobs consume at their pipeline positions through the engine's decision cores - `ip_whitelist`/`ip_blacklist` (the `RouteIpGate` arm before the global gate: a configured whitelist takes over the route verdict and skips the global lists, `skip_ip_lists`; the blacklist denies the reference `403 Forbidden`; an invalid entry fails secure), per-route countries (`blocked_countries`/`whitelist_countries` through `geo::check_countries`, a passing route whitelist skipping the global geo stage, `skip_countries`; no geo handler leaves the request alone), `required_headers` plus the auth group and the api-key group (`headers_auth::decide` over the carrier rules with the route verifiers, the `required` sentinel, the fixed `401` shape), `custom_validators` (`decide_custom_validators` under the reference `anonymous` name, the validator's own status, the truthy non-response and the declining validator passing through), `require_referrer` (the referrer core's `403` shapes), `time_restrictions` (the `start`/`end`/`timezone` dict through the time-window core, missing bounds fail-open), and `enable_suspicious_detection = false` skipping the scan for its route (`detection_enabled`); fourteen end-to-end twins drive every knob on a matching route and its off-route silence
- The `security_headers_applied` funnel (the H6 actix leg, over guard-core-rs#103's composer and #104's accessor): when the security-header set lands on a forwarded response and the bus is installed, the response pass composes `security_headers_applied_event` and dispatches it over the bus - action `headers_added` over the `security_headers` handler, metadata `path` (display-redacted), `headers_count` (the rendered set, before the CORS verdict and the response modifier touch the view), `has_csp`, `has_hsts`; guard-generated answers (blocks, the redirect, the oversize/failure shapes) apply the headers without firing, the reference's `create_error_response` lane where the event sits behind the request path, and a disabled set renders nothing and dispatches nothing; the funnel rides `run_response_processor` (the facts lane), with the generated lane staying on `run_response_processor_parts`
- The CORS preflight short-circuit and the behavioral usage rules in the pipeline (the GAP-R10 actix leg, over guard-core-rs#95's engine surface): an OPTIONS request carrying `access-control-request-method` answers from the resolved CORS config before every security check (`preflight_answer` over `cors::is_preflight` + `build_preflight_response`; the family plain-text body, the engine's preflight headers, no response-pass overwrite; CORS disabled or no response processor leaves OPTIONS to the pipeline), and the route carrier's usage/frequency `behavior_rules` track per request through the response processor's shared tracker with a crossed `ban` landing in the shared ban manager and rendering the activity-banned shape (the reference `process_usage_rules`, dispatched from the request pass before the check pipeline)
- The maintenance trio and the full status payload (the GAP-R9 actix leg): `GuardTransform::reset` (the reference `reset()`: the rate-limit windows drop, bans and violation counts untouched), `refresh_cloud_ip_ranges` + `with_cloud_refresh_scheduler` (the reference `refresh_cloud_ip_ranges`: one single-flight background refresh through the facade's `CloudRefreshScheduler` - the refreshed ranges land in the shared table, each provider's row restamped, `false` with no scheduler installed or while one is in flight, the reference's concurrent-caller gate), and `agent_stats` answering the reference property's no-agent shape (`{"enabled": false, "degraded": false}`, the `AgentStats` type); the status payload's provider rows carry the reference `get_status` shape - `ready`, `last_refreshed` (the unix-second stamp of the last range load, `null` before one, from `CloudIpTable::provider_status`), and `entries` - with the geo-ip component rendering the `IpInfoManager` health snapshot (`{ready, last_refreshed, entries}`) when the lifecycle manager is wired (the bare `configured` flag and `null` stay for the trait-only and absent arms)
- The reference route-config carrier consumption (`GuardTransform::with_route_configs`, the GAP-R2 actix leg): the engine's `RouteConfigResolver` (`(method, path) -> Option<Arc<RouteConfig>>`) resolves the route's `RouteConfig` per request - an `Arc<RouteConfig>` request extension wins over the resolver (the reference `request.state.route_config` idiom) - and the pipeline consumes it with the reference semantics: `bypassed_checks` (and the `"all"` wildcard) skip the named reference checks at their pipeline positions (the fused stages map as documented: `required_headers`/`authentication` skip the headers-auth stage, `ip_security` skips the gate, ban, and geo arms, `suspicious_activity` skips the scan and its violation feed), `require_https` rides the HTTPS stage's carrier lane (`decide_route`, the same trust knobs and passive handling as the global arm; with no stage installed the route arm still composes the reference `301`), `max_request_size` replaces the body cap for the route, `blocked_user_agents` runs additively before the global filter through the trusted-compile lane (a non-compilable route pattern fails secure `500`), the rate-limit group becomes the route's tier (an invalid tier fails secure), and the detection-exclusion group resolves through the engine's detection view; `RouteConfig`/`RouteConfigResolver` re-exported
- The unified-config consumption (`GuardTransform::from_security_config`, the GAP-R1 actix leg): the 129-field `SecurityConfig` (the fieldized reference surface in guard-core-engine) builds the wired pipeline in one call - the detection budgets onto `DetectConfig`, the IP lists onto the gate, the rate-limit knobs onto the limiter, the ban group onto `IpBanManager` + `IpBanConfig`, `enforce_https`/`trust_x_forwarded_proto` onto the HTTPS stage, `emergency_mode` + its whitelist onto the emergency stage, `custom_error_responses`/`on_block` onto the response surface, the detection-exclusion group (with the reference's empty-set-disables-all-categories semantics) onto the scan, the observability group (level, mutes, the three sensitive sets) onto the log/redaction knobs, `blocked_user_agents` onto the user-agent stage (ReDoS-validated, failing closed), and the security-headers/CORS/behavior group onto the response processor; invalid values fail closed through the new typed `GuardConfigError`; the reference `exclude_paths` carve-out lands as a first-class builder consumed first in the pipeline (an excluded path bypasses every request-side check, gate included, the response pass still renders); `SecurityConfig`, `SecurityConfigError`, and the `LogLevel`/`LogFormat`/`BufferOverflowPolicy` knob enums re-exported

### Changed

- The bypass consumption now uses the reference's coarse query vocabulary (the ip gate, the route IP restrictions, and the country arms query `ip`; the ban arm `ip_ban`; the cloud-provider check `clouds`; the rate limiter `rate_limit`; the penetration scan `penetration`; the `"all"` wildcard matches every query) - the previous wave keyed the bypass on the 17 stage names, a vocabulary the reference never queries (the stages it named are not route-bypassable in the reference at all, and their bypass conditions are removed); the `require_https` carrier lane falls back to the HTTPS stage's own resolver seam when no carrier route applies, and the custom-checks seam passes the buffered body through (`decide_custom_request`/`decide_custom_validators` take the body, guard-core-rs#86's validator-body contract)
- The IP-gate denial path now renders the reference ip_filter behavior end to end: passive mode logs the crossing and forwards (no block, no gate decision downstream), the `on_block` hook fires once with the reference payload keys (`ip_security`), and the custom-error body override wins over the family default - previously the gate denial rendered the family body unconditionally and skipped both
- The CI coverage gate computes line coverage from the lcov export's per-line DA records instead of llvm-cov's summary table: llvm-cov 22's summary aggregation falsely reports missed lines that no line-level view (show text/html, lcov, cobertura, the JSON segment list) can see on the same profdata, and the divergence persists on the newest available toolchain (cargo-llvm-cov 0.9.1 + rustc 1.99.0). The gate keeps the same fail-closed 100%-lines semantics with nothing hidden or excluded; the summary table stays in the job as an informational printout. Evidence linked in the workflow (#34)

## [1.2.0] - 2026-09-27

### Note

- Trains with the engine: `guard-core-engine` and `guard-core-rs` floors move to 4.2.0 (the 4.1.0 engine dists were yanked; this release restores registry resolution)

### Added

- The wave surfaces are publicly configurable on `GuardTransform`, each wired to the engine facade's rate-limit stage (`guard_core_rs::tower::RateLimitStage`, which the transform now builds and delegates every stateful decision and emission to):
  - `with_route_tiers(resolver)` (`path -> Option<RouteRateLimits>`; a `RouteRateLimits` request extension wins over the resolver) and `with_geo_handler(Arc<dyn GeoIpHandler>)`: the reference's endpoint/route/geo rate-limit tiers; the first tier that crosses answers the same `429 + Retry-After` shape and feeds the auto-ban engine
  - `with_detection_exclusions(DetectionExclusionConfig)` plus the `RouteDetectionExclusions` request extension: the reference per-route detection-exclusion surface, resolved per request through the engine's `detection_exclusions::resolve` + `scan_request`
  - `with_event_bus(Arc<SecurityEventBus>)`: the `penetration_attempt`/`rate_limited`/`ip_banned` events with the reference fields, metadata, and redaction
  - `with_observability(ObservabilityConfig)`: `log_suspicious_level`, `muted_check_logs`, and the `log_sensitive_headers/params/body_fields` redaction sets
  - `with_on_block(OnBlockHook)` and `with_custom_error_responses(CustomErrorResponses)`: the hook fires exactly once per blocked request (and per passive-flagged detection with no status); the status-to-body map overrides every block body, the `400` detection block included
  - `with_distributed_store(window_store, redis_prefix, redis_fail_open)` + `with_distributed_ban_store(store)`: the reference distributed mode (fail-closed backend errors answer `503 "Redis rate limiting unavailable"`, `fail_open = true` degrades to the in-memory window)
  - `with_passive_mode(bool)`: the reference passive mode - windows and counters record, log lines and events fire, no block ever renders
- New re-exports: `DetectionExclusionConfig`, `RouteDetectionExclusions`, `GeoIpHandler`, `BanStore`, `SlidingWindowStore`, `ViolationCounters`, `RouteRateLimits`, `RateLimitEntry`, `RateLimitTier`, `TierDecision`, `SecurityEventBus`, `ObservabilityConfig`, `RequestObservation`, `StageResponse`, `BlockPayload`, `OnBlockHook`, `CustomErrorResponses`

### Changed

- `guard-core-rs` (the engine facade) joins `guard-core-engine` as a pinned 4.1.0 dependency with the sibling-checkout path fallback; the stage delegation is an implementation detail behind the existing `with_rate_limiting`/`with_ip_banning` signatures, which keep their shared-handle semantics through the stage builder's `limiter`/`ban_manager` injection seams
- Scan semantics move onto the engine's reference surface: the query string is scanned as `parse_qsl`-decoded per-parameter pairs (previously one raw encoded blob), and the headers the exclusion resolution marks are scanned with their known false-positive categories suppressed (`ssrf` for address-chain values) instead of an adapter-level blanket skip. Exempt IPs now feed the violation counters (the reference suspicious-activity stage skips a whitelisted IP only; detection still scans and blocks them), so a crossed threshold bans even an exempt attacker


### Added

- Stateful stage (rate limiting, dynamic bans, auto-ban) over the engine's `rate_limit` and `ip_ban` modules, mirroring the tower reference implementation:
  - `GuardTransform::with_rate_limiting(RateLimiter)`: the sliding-window limiter runs after the IP gate and the ban check, before body buffering - a crossing answers `429 Too Many Requests` with `Retry-After: <window seconds>`, the references' rate-limit shape. With the limiter's `enable_rate_limit_auto_ban` on, every crossing counts one `rate_limit` violation toward the auto-ban engine (`threat_ban_config["rate_limit"]` first, then the flat threshold), the reference pipeline's `_record_rate_limit_autoban`
  - `GuardTransform::with_ip_banning(IpBanManager, IpBanConfig)`: a live ban answers `403 Forbidden` (`IP address banned`) before the limiter, so banned traffic never consumes rate budget; every detected threat counts its categories per client IP (the reference pipeline's suspicious-activity stage) and a crossed `threat_ban_config` entry or the flat `auto_ban_threshold` bans on the spot, answering `403 Forbidden` (`IP has been banned`); `config.enable_ip_banning = false` counts violations but never bans; the plain detection block keeps the reference suspicious-activity stage's `400 Bad Request` (`Suspicious activity detected`) shape
  - both stages honor the `exempt_ips` contract: whitelisted and exempt IPs are never rate limited, never banned (ban stage), and never have violations counted - which makes `exempt_ips` observable under load; unattributed requests (no peer address) cannot be held responsible and skip the stage, detection still screens them
  - the limiter, ban store, and violation counters are shared across all workers through an `Arc`, and `RateLimiter`, `IpBanManager`, and `ViolationCounters` are cheaply clonable and clone-share their stores, so out-of-band handles (admin unban endpoints, stats) work alongside the installed transform

### Changed

- Detection blocks answer `400 Bad Request` (`Suspicious activity detected`) instead of `403 Forbidden`, matching the reference suspicious-activity stage's status and the rest of the Rust family (the IP gate's `403 Forbidden` and the fail-secure `500` are unchanged)

## [1.1.0] - 2026-09-26

### Added

- Optional global IP gate (`GuardTransform::with_ip_gate` over the new engine `IpGateConfig`): `whitelist`, `blacklist`, and `exempt_ips` lists parsed once at startup (invalid entry is a config error, fail closed), evaluated before body buffering - a blacklisted client IP, or one a non-empty `whitelist` matches neither directly nor through `exempt_ips`, is denied with `403 Forbidden`. `exempt_ips` is the skip-list for known-friendly automation: it sets the same skip state a whitelist match sets (`IpGateDecision`, inserted into the request extensions) but never adds a deny path and never opens the whitelist gate; the blacklist and detection still apply to exempt IPs. The client IP is the request's peer address, so unattributed requests (no peer) are not gated and still screened by detection

### Changed

- `guard-core-engine` dependency pinned to the published 4.1.0 release (path dep kept for local builds and CI against a sibling `guard-core-rs` checkout), carrying the stateful sliding-window rate limiter and dynamic IP ban engine, the tower stage with a reusable `decide()`, and the new detection stages (request size/content, user-agent, headers/auth, cloud provider blocking, geo blocking)
- The buffered request body is no longer scanned as one lossy blob: it is routed by content type through the engine's body-value extraction (guard-core 4.0.4 parity, upstream commit 5f399234), and every extracted value is scanned through the normal detect path with its reference context - urlencoded field values under `request_body:form_field`, multipart part entries (label scan, `filename="..."` entry with RFC 2231 handling, raw part headers, payload) under `request_body:multipart_field`, embedded JSON leaves under the `:embedded_json` suffix, JSON mongo operator keys (`$where`, `$ne`, ...) as direct `nosql` hits, and the whole-body blob only as the fallback for plain or unparseable bodies
- Binary-dense multipart file-part payloads are reduced to printable runs of at least `detection_binary_min_run_length` (default 16) before pattern scanning, so compressed upload bytes stop producing attack-shaped matches while text embedded in uploads still scans in full; text uploads, text parts without a filename, and whole-body fallback scans keep their full scan
- 403/413/500 short-circuit responses now carry the bare message (`Suspicious activity detected`, `Payload too large`, `Security check failed`) as `text/plain; charset=utf-8`, matching the Python family's block-response convention, instead of the JSON `{"detail":"..."}` shape
